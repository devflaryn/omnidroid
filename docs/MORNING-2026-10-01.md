## Phase B — emulation-layer debugger (`crates/omni-debug`)

Loads a guest arm64 library on the translating backend (per-thread cache so breakpoints are allowed,
D38) and drives it below the guest. Built only on primitives that already existed (omni-cpu
breakpoints/thunks/return-sentinel, omni-mem W^X + copy-on-write, omni-elf symbols); no OS access of
its own. **Verified cross-OS:** `tests/lab.rs` 12/12 on Windows, Linux and macOS, plus the same over
MCP.

**Demonstrated on the real target:** driven over MCP against the cached real `libroblox.so`
(109 MiB, 543 exported symbols): `dump_module` produced a 120 MB in-memory image, and
`call_function` on the real engine's base64 decoder (`libroblox+0x2c11e34`) returned **11/11**
correct results for crafted inputs — a real Roblox engine function exercised directly, no game, no
login, no anti-cheat.

### How to call the Frida-style debug tool (one line each)

```jsonc
// tools/call lab_load      {"path": "/path/to/lib.so"}
// tools/call call_function {"symbol": "adler32", "args": [1, "0x40000000", 14]}   // crafted inputs, no game
```

## Phase C — perf: what was measured, and why nothing risky was landed

Baseline and census, Delta APK in PS99 in-world, on `main` (which already includes perf-win). Harness
committed as `tools/perf_inworld.ps1`.

### Before / after

No optimization was landed overnight, so there is no "after" — deliberately. The measured **baseline**
(the state you're on) and the **census** that pins it:

| metric (guest-host processes, in-world steady) | baseline | census run |
|---|---|---|
| private bytes, median | 4.39 GB | 4.49 GB |
| working set, median | 5.28 GB | 5.10 GB |
| on-screen present fps, median | 16.3 | 16.6 |
| host processes (peak) | 9 (→7) | 8 |

The **~100 MiB gap between two identical-code runs is the finding**: in-world private bytes has that
much run-to-run variance (which background app processes are alive, when trimming fires), so any safe
lever below ~100 MiB can't be attributed from a single before/after.

### The app host process, pinned (commit 2746 MiB)

| part | MiB | movable? |
|---|---|---|
| engine guest heap (mimalloc, live data) | 1806 | no |
| shared translation cache | 236 | already tuned (256 live; 128 was too low, D38 amд 4) |
| app's own Vulkan memory | 273 | no (render targets/buffers) |
| **host-side remainder (GPU driver pools + overhead)** | **~430** | **= perf-win's "~512 MiB unexplained"** |

**So the "~512 MiB" is the host NVIDIA driver's own pools in the app process, not an app allocation.**
Reducing it needs Vulkan allocator/budget work in the forwarding layer — host-specific and risky.

### Observation to verify (not chased)

The on-screen present rate measured **~16 fps**, about half of perf-win's documented 33.5. Most likely
a busier live world at the time (US daytime), not a regression (this is the same `main`), but worth a
re-measure at a quiet hour.

### Parked, with why

- **No speculative RAM change landed.** Every safe lever is at/below the ~100 MiB variance floor for a
  single A/B, and the changes that might pay (host-driver Vulkan memory; trimming more app host
  processes like `providers.media.module`/`ext.services`, ~100 MiB each) risk a subtle in-world break
  a content-provider disable can cause — only multi-run soak testing catches that, which I can't
  supervise unattended. Autonomous ≠ reckless.

## Top 3 next levers (for a supervised session)

1. **Faster translated code (SPEED).** The render thread is guest-compute-bound (~100% of a core,
   perf-win). Biggest fps lever and the one that remains; dynarmic optimization work.
2. **Batch the ~2240 Vulkan calls/frame (SPEED).** perf-win estimated ~half of the render thread's
   ~8% forwarding cost recoverable; a real change in the Vulkan forwarding layer with a clear metric.
3. **Trim more background app host processes (RAM, ~200–400 MiB).** Extend `device::LEAVES_OUT` with
   media.module/ext.services etc., validated over several soak runs to confirm no in-world regression.
