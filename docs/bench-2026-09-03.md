## Third pass 2026-09-03: guest Vulkan via venus — NEGATIVE on a Windows host
Premise (HANDOFF-VENUS.md): MuMu on this PC gets ~75 fps avg (80 peak) on the same APK/game where OmniDroid gets ~44; MicroProfiler showed GPU only ~21% busy and ~10ms of a ~22ms frame stalled in queryOcclusion (5-9ms) + Present (5ms) -- virgl's synchronous host round-trip per occlusion query, vs MuMu's async Vulkan/native path. Task: rebuild libvirglrenderer-1.dll with venus, wire venus=on,blob=true,hostmem=1G, measure.

Build (msys2 mingw64, virglrenderer 1.3.0, tools/virglrenderer-venus/): DLL built clean after 7 small mingw ports (getpagesize, mman_win32.h, dlfcn.h guard, sys/resource.h, setpriority->SetThreadPriority, thrd_current->GetThreadId; full list in venus-mingw-1.3.0.patch). Exports byte-identical to stock (96/96, diff empty), +1.1 MB of venus/vkr code (2,002,464 vs 881,380 bytes), only new import is vulkan-1.dll (resolves to the NVIDIA System32 loader). `strings | grep -ic venus` is degenerate (1 on both new and stock -- one literal compiled into virglrenderer.c regardless of ENABLE_VENUS); the real discriminators are the export diff and `objdump -p | grep -c vulkan-1.dll` (0 stock, 1 new).

Blocker A -- render server is POSIX-only. In virglrenderer 1.3.0, `struct vkr_context` no longer subclasses `struct virgl_context`; every venus capset entry point routes through the proxy/render-server. The real venus init, `vkr_renderer_init()`, has exactly one caller in the tree -- `server/render_state.c:156`, inside the separate `virgl_render_server.exe`; `proxy_renderer_init()` (`virglrenderer.c:931`) is the only way the library reaches it, gated on `VIRGL_RENDERER_RENDER_SERVER`. QEMU's `virtio-gpu-virgl.c:1567` sets `VIRGL_RENDERER_VENUS | VIRGL_RENDERER_RENDER_SERVER` together for `venus=on`. Building the render server on mingw hits 8 immediate missing-header failures across `src/proxy/` + `server/` (poll.h, sys/wait.h, sys/socket.h, sys/mman.h, sys/signalfd.h, syslog.h); its API census (grep over `src/proxy/`+`server/`): eventfd 31, sendmsg/recvmsg 6, SCM_RIGHTS 4, socketpair 2, fork 2, execv 1, plus signalfd and epoll -- none of it has a Windows equivalent. Not attempted (outside this task's mandate).

Blocker B -- venus's memory export is fd-only. Independent of A: venus exports host Vulkan memory to the guest exclusively through POSIX fds/dma_buf (`vkr_device_memory.c:533-567`, `vkr_context.c:266,291`); zero Win32-handle support anywhere in src/venus/. `vkr_allocator_init()` hard-requires `VK_KHR_external_memory_fd`. Measured on this host with a purpose-built probe (tools/virglrenderer-venus/vkprobe.c) against the RTX 4060's Vulkan 1.4.325 driver: `VK_KHR_external_memory_fd: NO`, `VK_EXT_external_memory_dma_buf: NO`, `VK_KHR_external_memory_win32: YES`. fd/dma-buf handle types have no Windows counterpart in practice -- no Windows ICD exposes them, and this one does not (probe: fd NO, dma_buf NO, win32 YES).

Measured launch (task-3b): swapped the venus DLL into a `C:\qemu-omni-venus` copy, launched with `virtio-gpu-gl-pci,xres=1920,yres=1080,venus=on,blob=true,hostmem=1G`. qemu.log, verbatim:
```
qemu: failed to get xsave state: No error
Render server support was not enabled in virglrenderer
failed to initialize venus rendererqemu: virgl could not be initialized: -1
```
QEMU keeps running and the guest boots with NO GPU at all -- worse than GLES, never enable by default. `sys.boot_completed=1` at 1.7 min and Roblox joined the place (manager.py `"played": true`), but logcat shows `MESA: No virgl contexts available on host` and repeated `DRM_IOCTL_VIRTGPU_GET_CAPS failed with Function not implemented` across every process that probed the GPU; `dumpsys SurfaceFlinger` timed out twice, consistent with a degraded/non-accelerated renderer.

Conclusion: OmniDroid on Windows is virgl-GLES-bound. Closing the 44-vs-75 gap needs MuMu-parity via a Win32-handle venus port upstream (fd/dma_buf -> external_memory_win32 throughout vkr_device_memory.c/vkr_allocator.c, plus an in-process transport replacing the render server) -- or a different host GPU backend, or a Linux host. None of those is this task. What remains true: `OMNI_VENUS=1` (ac797b7, `omnidroid/qemu_proc.py`) exists as an A/B gate and is inert/harmful on Windows -- it makes `virgl_renderer_init()` fail and the guest lose GL entirely. Do not enable it by default.

## Fourth pass 2026-09-03 (session 646bf8ae): event-driven fences -> the fence poll IS the constraint, via vsync doubling
Setup: QEMU 11.1.0 +0001-0015 (C:\qemu-omni-next, rebuilt), Skylake-Client-v4, smp 8, 4096 MB, window on 144 Hz panel, GPU pinned P0 2475 MHz (7-15% util), admn1b12farm2 / PS99 / offset 2.735.1138-lock2, zaphub disabled, world confirmed on screen every sample.

Corrects the first pass's "fence poll interval is NOT the constraint". That A/B (38 vs 38) happened to land both boots ABOVE the vsync boundary. Re-measured:

| setting | fps (2x30s, +confirm) | missed | present p50 | fence latency avg | profiler avgFrame |
|---|---|---|---|---|---|
| default 10 ms poll | 21.6 / 21.9 | 324 / 307 | 46.2 ms | 12-15 ms | 38.4 ms |
| QEMU_VIRGL_FENCE_POLL_MS=1 | 44.1 / 43.0 | 0 | 21.6 ms | ~1 ms | 28.0 ms |
| patch 0015 fence watcher (default poll) | 44.5 / 46.0 / 47.2 | 0 | 21.0 ms | 0.3-0.5 ms | 24.3 ms |
| watcher + idle=poll | 31.1 / 35.2 | 68 / 4 | 25.7 ms | 0.5 ms | -- (idle=poll oversubscribes the 8 cores; DISCARD) |

The 10 ms control MISSED half its frames and present p50 was exactly ~2x the good run: the frame lands just over the display deadline and waits a full refresh. Dropping fence latency pushes it back under the boundary and fps DOUBLES. This is the "22-25 one day, 47-53 the next" the FPS handoff could not explain -- boot-to-boot the frame sat just over/under the boundary.

patch 0015 (omni-win32-fence-watch): after virglrenderer creates its GL fence (same thread/context), arm our own glFenceSync; a watcher thread with a shared WGL context blocks in glClientWaitSync and schedules a BH that runs the fence poll the instant the GPU signals. Same effect as the 1 ms busy-poll without a 1 ms main-loop wakeup, and lower latency. armed==fired every second (no leaks); ~90 fences coalesce to ~55-84 wakeups. OMNI_FENCE_WATCH=0 disables; no-op off Windows; farming (headless, no WGL) falls back to the timer. Committed 5567ee7.

MicroProfiler under the watcher (render-thread EXCLUSIVE ms/frame): queryOcclusion 7.3 (6.5 calls), Present 5.5, updateRenderQueue 3.0. Fence latency is no longer the cost -- these are GPU-completion stalls (occlusion-query readback waits for the depth pass; Present waits for frame finish). GPU 15% util, guest 70% idle -> serialization-bound, not compute/GPU-bound. The remaining 47 -> 80 gap is these per-frame CPU<->GPU sync points, inherent to virgl's split renderer. Hiding them needs async occlusion (read last frame's query result; 1-frame culling latency) or MuMu-style in-process rendering (venus is dead on Windows, see HANDOFF-VENUS). INVALID reading to avoid: a boot that sat on the Roblox home/BIG-Games loader read 53-59 fps at clientComp=100% (2D UI, not the world) -- always confirm clientComp=0 + a world screenshot.
