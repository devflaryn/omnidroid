## Measurement

`tools/perf_ab.ps1` (one run of a prebuilt `r_roblox` test binary = one *arm*; boot, sign in, join
PS99, settle 75 s, measure 150 s) and `tools/perf_ab_seq.ps1` (a sequence of arms, ABBA order).
Per run, one CSV row:

| column | what |
|---|---|
| `fps` | presented frames / s over the window, exact (from consecutive `[display]` lines) |
| `top_ms` | busiest thread of the app's host process (the engine worker), CPU ms per frame |
| `top2_ms` | second busiest (the render thread), CPU ms per frame |
| `app_ms` / `all_ms` | the app's host process / every guest host process, CPU ms per frame |
| `priv_gb` / `app_priv_gb` | median private bytes, all guest host processes / the app's |

Thread CPU is read from Windows (`Process.Threads`), so nothing inside the guest host is perturbed
(OMNI_THREAD_CPU's 100 Hz suspend/resume sampler is left off for A/B runs).

## Findings from the host-side census (tools/vmcensus.ps1, read-only)

The system's host process (`system_server` + ~68 guest processes, ~900 host threads), mid-boot,
~1.7 GB private:
- **Property areas, private per guest process, fully committed.** ~80 allocations with the prop
  area magic (`PROP`, version `0xfc6ed0ab`), 1.13 MiB each, ~90 MiB -- `mm.rs` writes the whole
  area (capacity ~1.1 MiB, ~61 KiB used) into fresh anonymous memory in every process that maps it.
- **The NT heap** (Rust + dynarmic's C++): 25 segments = 347 MiB, plus many direct large blocks
  (1-16 MiB) -- the biggest non-guest chunk. Known inside it: code-cache tables (~86 MiB), a 64 KiB
  fast-dispatch table per guest thread (~900 x 64 KiB = 56 MiB).
- Guest memory in 64 KiB pieces (~205 MiB), translation caches (exec, ~290-530 MiB before trims).

### Linux runs leak RAM when killed (found at ~06:50)

Runs 10-12 died in boot (`SettingsProvider`: `SQLITE_CANTOPEN` on settings.db -> system_server
SIGKILLs itself, the instance goes down). Cause: every killed r_roblox run leaves its gralloc regions
in **/dev/shm** (2,562 `omni-shm-<pid>-*` files, 457 MB) and its instance directory in **/tmp** --
both tmpfs, i.e. RAM, on a 7 GB machine. Cleaned (only regions of dead pids); a janitor now deletes
dead runs' regions and directories every 45 s. **For the runtime:** an instance that is killed
(not shut down) never unlinks its shm regions on Linux; unlinking them right after both sides have
mapped them (as memfd would behave) would make that leak impossible.
### Correction to last night's "~430 MiB = the NVIDIA driver's pools" (app host process)

Reading the headers of the app host's 16-64 MiB private blocks (read-only, in-world): the 24-32 MiB
ones carry the NT heap's large-block header -- they are heap allocations, the code cache's robin-map
tables among them (block map 32 MiB, link targets 24, block links 24.6, fastmem sites 24.8, guest
ranges 20.5 MiB at ~567k blocks: 124 MiB, OMNI_MEM_TRACE's census). So part of the "~430 MiB
host-side remainder" pinned on the GPU driver last night is our own heap; the driver's share is
smaller than that figure.
