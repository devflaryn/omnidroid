## Top-3 remaining levers (ranked by expected payoff)

1. **The system host's per-frame CPU: a zero-copy present.** The system's host process spends ~111
   of the ~205 ms of CPU per frame (at 26 fps, ~2.9 cores) — more than the game's own process.
   Every frame crosses the CPU five times at 3.7 MB each: GPU → staging → gralloc shm (release
   worker), shm → composed frame (composer; C4 makes that pass ~6× cheaper), → framebuffer, a clone
   for the present thread, RGBA → BGRA for GDI, then GDI's own blit. When the composer has one
   full-screen layer (the in-world case), presenting the app's `VkImage` straight into a host
   swapchain removes the GPU readback and four of the CPU passes. Biggest CPU/latency lever left
   outside the game's own code (the engine worker is only ~75% busy — the frame is a cross-thread
   path, so this is where fps can come from).
2. **RAM in the system host and the small app hosts.** After the prop areas: the ~900 threads'
   64-KiB fast-dispatch tables (patch 0035 is in, default off: one in-world A/B of the system host's
   CPU with `OMNI_JIT_FAST_DISPATCH_SYSTEM=1024` decides −42 MiB), the NT heap (~350 MiB of segments
   + large blocks: needs a heap census by owner), and five small app host processes at ~85–100 MiB
   each (~450 MiB: media.module, ext.services, networkstack, the IME, webview_zygote) — zygote
   pages shared across them (fork-after-load) is the structural fix.
3. **What cost measurement time tonight (robustness):** the kiosk image has **no browser**, so any
   app that opens a link crashes (Delta's key-system link killed a whole session); and the A/B
   harness guard refused to boot below a stale ~13 GB free-commit threshold when your games took the
   host from 05:44 on — but an instance actually commits only **~3 GB** (measured ~3.7 GB across its
   7 processes in-world), so that guard is over-conservative and should be ~4–6 GB. A VIEW-intent
   stub and a corrected boot guard would make overnight A/Bs reliable.
